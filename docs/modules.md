# Module catalog

Every Azure resource this template can deploy lives in the catalog under
`infra/modules/`. A catalog module is self-describing: it carries its own
contract, its own documentation, and its own test stub, so preflight, the
private DNS zone list, and the tables on this page are all derived from it
rather than hand-maintained.

The catalog is the enrichment mechanism. When a module proves itself in a real
project, [promote it back](#promoting-a-module-from-another-repository) and
every future project starts with it.

## Anatomy of a module

```text
infra/modules/<module-name>/
  main.bicep      the module itself
  metadata.json   the contract
  README.md       purpose, parameters, and a copy-paste wire-up snippet
```

Three artefacts are generated from `metadata.json` and must never be edited by
hand:

| Generated file | Generated by | Consumed by |
|---|---|---|
| `infra/modules/catalog.json` | `scripts/build-catalog.ps1` | preflight, the lifecycle scripts, and this page |
| `infra/core/private-dns-zones.json` | `scripts/build-catalog.ps1` | `infra/modules/private-dns/main.bicep` |
| the tables below | `scripts/build-docs.ps1` | you |

`scripts/build-catalog.ps1 -Check` and `scripts/build-docs.ps1 -Check` fail when
those files are stale. Both run in CI and in the test suite.

## The module contract

Conformance is enforced by `tests/catalog.tests.ps1`, not by convention.

**Required parameters** — `name`, `location`, `tags`.

**Required outputs** — `id` and `name`, for every module with
`"kind": "resource"`. A `composite` module deploys several resources and is
exempt, because there is no single resource to identify.

**Private endpoints are optional, always.** A module that supports Private Link
accepts `privateEndpointSubnetId` and `privateDnsZoneId`. When both are empty
the module deploys public-with-firewall; when they are set it calls
`infra/core/private-endpoint.bicep`. That is what lets one module body serve all
three profiles: a `core` project and a `full` project run identical module code,
and only the wiring differs.

### `metadata.json`

```jsonc
{
  "name": "service-bus",                 // must match the folder name
  "displayName": "Service Bus namespace",
  "description": "One sentence on what it deploys and why.",
  "kind": "resource",                    // resource | composite
  "abbreviation": "sbns",                // must exist in infra/core/abbreviations.json
  "additionalAbbreviations": [],         // extra names a composite claims
  "featureFlag": "serviceBus",           // the enable* flag, or null if always on
  "profiles": ["core", "private", "full"],
  "providers": ["Microsoft.ServiceBus"], // drives preflight registration checks
  "privateEndpoints": [
    {
      "zoneKey": "serviceBus",
      "groupIds": ["namespace"],
      "dnsZone": "privatelink.servicebus.windows.net",
      "linkSuffix": "sbns",
      "connectionName": "service-bus"
    }
  ],
  "roles": [
    { "name": "Azure Service Bus Data Owner", "id": "090c5cfd-751d-490a-894a-3ce6f1109419" }
  ],
  "nameRule": "regional",                // regional | global | globalCompact | hostname | fixed
  "preflight": { "checks": [], "requiresOperatorPrincipals": false }
}
```

Two fields deserve a note:

- **`privateEndpoints` is an array, not a single object.** A storage account
  needs separate blob and file endpoints with separate DNS zones, so one entry
  per endpoint is the only shape that works. A module with no Private Link
  support declares `[]`.
- **`nameRule: "fixed"`** means the service dictates the resource names, so the
  convention does not apply. Only a `fixed` module may declare a null
  `abbreviation`; `private-dns` is the one example, because a private DNS zone
  is named after the zone itself.

`linkSuffix` and `connectionName` are part of the deployed resource names. Once
a module has been provisioned anywhere, changing them replaces resources.

## Lifecycle scripts

| Script | Purpose |
|---|---|
| `scripts/new-module.ps1` | Scaffold a new catalog module |
| `scripts/add-module.ps1` | Wire a catalog module into `infra/main.bicep` |
| `scripts/promote-module.ps1` | Bring a module proven elsewhere into this catalog |
| `scripts/adopt-conventions.ps1` | Push the conventions layer into an existing repository |

### Authoring a new module

```powershell
./scripts/new-module.ps1 -Name service-bus -Abbreviation sbns `
  -Provider Microsoft.ServiceBus `
  -ResourceType Microsoft.ServiceBus/namespaces -ApiVersion 2022-10-01-preview
```

This creates the folder, a `main.bicep` skeleton that already satisfies the
contract, `metadata.json`, a README, and `tests/modules/service-bus.tests.ps1`.
It also regenerates the catalog. Add the abbreviation to
`infra/core/abbreviations.json` first — the catalog tests fail if it is missing.

To scaffold a module with Private Link support, add the group ID and zone:

```powershell
./scripts/new-module.ps1 -Name service-bus -Abbreviation sbns `
  -Provider Microsoft.ServiceBus `
  -ResourceType Microsoft.ServiceBus/namespaces -ApiVersion 2022-10-01-preview `
  -PrivateEndpointGroupId namespace `
  -PrivateDnsZone privatelink.servicebus.windows.net
```

Other useful switches: `-Kind composite` for a module that deploys several
resources (which exempts it from the `id`/`name` output contract), `-Profiles`
to restrict which rungs it belongs to, and `-NameRule` to pick a class from
`infra/core/name-rules.json`.

Then fill in the resource body, and run:

```powershell
az bicep build --file infra/modules/service-bus/main.bicep
./tests/run-tests.ps1
```

### Wiring a module into a project

```powershell
./scripts/add-module.ps1 -Module service-bus
```

The script inserts the module block into `infra/main.bicep` between the
`// #region modules` and `// #endregion modules` markers, and is idempotent — a
second run reports `AlreadyPresent` and changes nothing. If the markers are
absent, or you pass `-PrintOnly`, it prints the snippet instead so you can place
it yourself:

```powershell
./scripts/add-module.ps1 -Module service-bus -PrintOnly
```

You still add the feature flag, the name variable, and the outputs by hand; the
printed snippet includes all four parts.

### Promoting a module from another repository

This is the path that grows the template. A module that has been deployed and
proven in a real project is copied back into the catalog:

```powershell
./scripts/promote-module.ps1 -From D:\path\to\project\infra\modules\service-bus -WhatIf
./scripts/promote-module.ps1 -From D:\path\to\project\infra\modules\service-bus
```

The script validates the source against the full contract *before* copying,
builds and lints it, copies only `main.bicep`, `metadata.json` and `README.md`,
regenerates the catalog, runs the catalog conformance suite, and rolls back if
anything fails. It refuses to promote a module that violates the contract.

### Adopting the conventions in an existing repository

`adopt-conventions.ps1` pushes `infra/core/**`, the shared scripts, the naming
instructions, and the `azure.yaml` hook block into a repository that was not
created from this template:

```powershell
./scripts/adopt-conventions.ps1 -Path D:\path\to\other-repo -WhatIf
./scripts/adopt-conventions.ps1 -Path D:\path\to\other-repo
```

It never touches the target's `infra/main.bicep`, `infra/main.parameters.json`,
`infra/modules/` or `azure.yaml`, and it refuses to overwrite a file the target
has modified locally unless you pass `-Force`. A `.azd-starter.json` stamp
records the template version applied, so a repository that has fallen behind can
be identified.

## Testing

```powershell
./tests/run-tests.ps1                 # everything
./tests/run-tests.ps1 -Name catalog   # catalog conformance only
./tests/run-tests.ps1 -Name bicep     # compile, lint, and the profile matrix
./tests/run-tests.ps1 -Name naming    # name equivalence and name rules
```

The catalog suite checks the contract files, the metadata schema, abbreviation
and zone-key uniqueness, catalog freshness, required parameters and outputs, the
public-capable branch of every Private Link module, and that every module's
providers are known to preflight.
